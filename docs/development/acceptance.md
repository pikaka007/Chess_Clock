# 验收计划（预期值先写，实现后逐条实测）

本文件在写任何计时代码**之前**填写。每条先给出可判定的预期值，再注明验证手段。
验证手段分三级，报告与 `docs/verification.md` 用同一套标注：

- **自动化（JVM）**：`:app:testDebugUnitTest`，用可控时钟驱动生产计时逻辑。
- **自动化（仪器）**：`:app:connectedDebugAndroidTest`，在模拟器/真机上跑 Compose UI。
- **人工实测**：在模拟器/真机上按步骤操作，记录截图与观察结果。

---

## A. 零增量（1 分钟预设，双方 60 000 ms，increment = 0）

| 步骤 | 期望 |
|---|---|
| 进入对局 | 双方 `1:00`，步数 `0`，状态 `READY`（"等待首次点击"） |
| 点击玩家二表盘（t=0） | 玩家二计时中，玩家一静止，步数仍 `0` |
| 3 000 ms 后点击玩家一（t=3000） | 玩家二 `57 000 ms`、玩家一 `60 000 ms`、步数 `1`、玩家一计时 |
| 再经过 2 000 ms（t=5000） | 玩家二 `57 000`、玩家一 `58 000`、步数 `1` |
| 暂停，静止 5 000 ms | 三项数值不变（`57 000 / 58 000 / 1`） |
| 继续后经过 1 000 ms | 玩家一 `57 000`、玩家二 `57 000`、步数 `1`（继续只恢复原计时方） |

补充断言：暂停期间点击双方表盘都不改变数值、不加步、不加秒。

## B. Fischer 3+2（双方 180 000 ms，increment = 2 000 ms）

| 步骤 | 期望 |
|---|---|
| 点击玩家二，3 000 ms 后点击玩家一 | 玩家二 `179 000 ms`（`2:59`，= 180 000 − 3 000 + 2 000）、玩家一 `180 000`、步数 `1` |
| 玩家一计时中，重复点击玩家一 3 次 | 状态完全不变：仍 `179 000 / 180 000`、步数 `1`，不额外加秒 |
| 暂停 4 000 ms 后继续 | 双方余时不变、步数不变；继续不触发加秒 |
| 换手时余时恰好为 0 | 判**超时**：该方 `0`、状态 `FINISHED`、`flagged = 该方`；**不加秒、不加步**，另一方不被启动 |
| 超时后再点击表盘 | 状态不变（不复活对局） |

增量归属规则：一次**有效换手**里，给**刚完成该步（被停表）的一方**加 increment，
然后步数 +1，再启动另一方。首次启动、暂停、继续、重复点击、超时后点击都不加秒不加步。

## C. 设置与重置

| 场景 | 期望 |
|---|---|
| 预设 1 min | 设置页显示 `1:00`，进入对局后双方 `1:00`，increment `0` |
| 预设 3+2 | 界面明示"每步 +2 秒"，进入后双方 `3:00`，换手后验证 B 的加秒 |
| 自定义 5 分钟（300 s） | 保存/进入后双方显示 `5:00`（AppForge AF-2/2-1 场景） |
| 自定义基础时长 = 0 / 空 / 负 / 非数字 | 拒绝进入对局并给出具体错误文案；不启动计时 |
| 基础时长上限 | 60 分钟（3 600 000 ms）内接受；超出提示上限 |
| 增量上限 | 0–60 秒；超出提示 |
| 重置 → 取消 | 恢复点击重置前的运行状态：原本在跑的继续跑（计时方不变），原本暂停的仍暂停；余时与步数不被清空，取消本身不产生额外加秒/加步 |
| 重置 → 确认（5 分钟对局，已走 3 步） | 双方回到 `5:00`、步数 `0`、状态 `READY`；确认文案写明"双方恢复至 5:00，步数归零" |
| 确认框打开期间 | 双方时间冻结（打开即自动暂停），读数不下降 |

## D. 恢复（分级报告，禁止混称）

| 场景 | 期望 | 手段 |
|---|---|---|
| D1 Activity 重建（旋转/夜间模式） | 余时按重建前状态续算一次，不加步不加秒；`moves`、`config`、`runningSide` 保留 | 仪器测试 + 人工 |
| D2 进入后台再返回（进程存活） | 后台时长**按真实经过扣除**（棋钟语义：离屏不等于暂停）；仅扣一次 | 仪器测试 + 人工 |
| D3 后台进程被回收后重新进入 | 从磁盘快照恢复：运行中 → 按快照锚点补扣一次；暂停 → 不扣；`READY` → 原样 | 人工（`adb shell am kill`）+ 存储层单元测试 |
| D4 用户强制停止（Force stop） | 与 D3 同路径（快照仍在），恢复后不出现"负时间"或双倍扣时 | 人工 |
| D5 设备重启 | 单调时钟基准失效 → **暂停恢复 + 明确提示**，不尝试跨重启相减 | 单元测试（换 bootId）+ 可行时人工 |

保存时机（明确写清，避免"每帧写盘"）：状态转换时（点击/换手/暂停/继续/重置/配置）、`ON_STOP` 时、
运行中每 10 s 最多一次的节流快照。渲染帧不写盘。

## E. 时间异常

| 场景 | 期望 | 手段 |
|---|---|---|
| 注入时钟让 now 跳跃 +30 s 而无 UI 刷新 | 下一次取值即补算 30 s，且只扣一次 | JVM 单元测试 |
| 修改系统日期/时区（同一次开机） | 剩余时间不受影响（逻辑只用单调源） | 单元测试（引擎不接收挂钟时间）+ 人工改时区 |
| now 早于锚点（异常/回绕） | 不产生负值，也不额外扣时（钳制为 0 增量） | JVM 单元测试 |
| 损坏快照（截断 JSON / 字段缺失 / 版本不匹配） | 丢弃并回到 `READY` 默认配置，不崩溃 | JVM 单元测试（存储层以可注入的字符串仓库测试） |
